# 决策记录的检查门禁：判什么、在哪一层判、以及它自己也要被它判

日期：2026-10-12
状态：已采纳
影响版本：afk-bootstrap 1.7.13（`upgrade-afk.sh` 的 `1.7.12 -> 1.7.13` 步骤）

## 背景

1.7.12 把「非平凡改动要写决策记录」装进了脚手架：一个检查器
（`adr.check.mjs`）、一份约定（`docs/agents/architecture-decisions.md`）、
三条实现提示里的纪律，以及策略任务里的一个 CI 步。

装完当场有三个缺口，都是**实测**发现的，不是推演：

1. **门禁会静默降级。** CI 里写的是
   `AFK_ADR_BASE: ${{ github.event.pull_request.base.sha || github.event.before }}`，
   两个来源都不存在时它求值为**空字符串**——而空字符串是假值。检查器原本用
   `ENFORCE = ALL || BASE !== ""` 决定是否拦，于是「配错了的 workflow」跑成
   一次绿色的报告，**长得和一次通过的门禁完全一样**。实测 `--base ""` → rc=0。
2. **这条规则不判自己。** 1.7.12 那笔提交改了 `.github/workflows/ci.yml`、
   `afk-policy.yml`、`upgrade-afk.sh` —— 全是它自己定义的「改动工具链」，
   却没带记录、也没留豁免行。用我们自己发布的 `--base` 门禁回判，它是**红的**。
3. **检索纪律没落。** 约定文档有「什么时候写」「怎么写」「怎么写得好」，
   唯独没有**「写之前先去查」**。而这一条是整件事的前提：一篇没人找得到的
   记录等于没有，而「三个月前否掉的路又被提一遍」正是这套东西存在的理由。

另有一条在设计评审里就暴露、但当时没当缺口记下的：**覆盖判定以整条 diff 为单位**
（`git diff <mergeBase> HEAD`），而不是以提交为单位。后果是一笔工具链提交会和
旁边一笔功能提交算在同一份 diff 里，**工具链那半替功能那半回答了**。1.7.11 与
1.7.12 两次改动的叠加就是这个形状。

## 决定

**三点，各自独立。**

### 一、门禁按「被要求」判定，不按「值」判定

```js
const baseRequested = argv.includes("--base") || hasOwnProperty(process.env, "AFK_ADR_BASE");
if (baseRequested && BASE.trim() === "") { /* 报错，rc=1 */ }
```

判据从**值**改成**规格**：`--base` 出现在命令行上，或 `AFK_ADR_BASE` 存在于
环境里（**包括存在但为空**），就是「要求判 diff」。要求了门禁却什么都没给，
是配置错误，按配置错误失败。

裸跑（两者都没有）仍是报告、rc=0 —— 迁移自己需要它，项目也需要在不管道时读它。

### 二、覆盖以提交为单位，不以 diff 为单位

每笔提交对它**自己的父提交**判定（`git diff-tree --root`，所以仓库的第一次提交
也能判）。范围取 `git merge-base <base> HEAD`..`HEAD`，所以**只是落后于 main 的
分支不会把 main 的提交算成自己的**。

结构那一半保持「只判本次改动碰到的记录」（`--base`）或「全树」（`--all`）；
`--all` 只管结构，不管覆盖 —— 「全树的记录形状」和「本分支的提交欠不欠记录」
是两个独立问题，`--all --base X` 是同时问两个的合法写法。

### 三、这条规则判自己

约定文档新增一节，写明检查器与它的 CI 接线**自己也是决策**，因此同样要带记录或
豁免行。1.7.12 那笔工具链提交就是反例。

## 被否掉的方案

- **去掉门禁，只保留报告。** 最简单，也确实回到 1.7.12 之前——代价是「该写却没写」
  没有任何东西会发现，而那正是全部价值所在。
- **让空 base 退回判全树**（1.7.12 的最初版本）。配错时至少还拦住了东西。但后果比
  不拦更糟：浅检出会把整个后台账的红一并报出来，**红落在下一个推分支的人头上**
  而不是落在造成它的配置上。已实测过：四个消费仓库的 CI 全部因此变红。
- **覆盖仍按整条 diff 判，但排除「工具链提交」。** 需要给每笔提交分类，而分类正是
  本检查声明自己不做的事（见下）。
- **把 `No-ADR` 做成需要签名的真豁免。** 签名对一个仓库内的自觉纪律是过度设计；
  一行读得懂的理由已经买到了想要的东西——**人读日志时能看见理由**。伪造它的成本
  和写一句真话一样，所以没有边际收益。

## 没有解决的（写清楚，而不是假装覆盖了）

检查器判不了两件事，都留给读 diff 的人：

1. **一笔提交既改了源码又加了记录，就算通过了** —— 哪怕那篇记录写的是另一回事。
   判这个要读散文。
2. **提交正文里只要出现 `No-ADR:` 就算豁免**，包括「我们讨论过 No-ADR 这个机制」
   这种句子。豁免是给人读的断言，不是认证过的凭据；装作它是，比它防住的谎更糟。

第二点在实现上收窄了一点：豁免只匹配**正文减掉标题**之后的内容，所以检查器自己
的说明文字（引用了 `No-ADR: <reason>`）不会满足它。

## 后果

- **收益**：门禁在配错时失败而不是变绿；一笔工具链提交不再替旁边的功能提交回答；
  写之前先查这一步进了约定，且是四法里最便宜的那条。
- **代价**：CI 里 `AFK_ADR_BASE` 两个来源都拿不到时**会红**，需要配 workflow 的人
  看一眼报错——这是要的，但它意味着首次接入的那次推送可能因为环境而非代码变红。
- **代价**：判定的粒度到提交，所以一笔把功能与工具链混在一起的提交，只要带了记录
  就算通过；把改动拆成两笔提交是唯一的出路，而检查器不强制拆分。
- **已知上限**：这套东西的全部价值押在「下一个人会先查再动手」上。检查器能保证
  记录**写下来了**、能保证它**有形状**，保证不了它**被读到**。读到与否只能靠观测：
  被否掉的路线是否还在被重新提出。

## 验证

`--base ""` 与 `AFK_ADR_BASE=""` 都必须 rc=1（实测）；裸跑必须 rc=0（实测）。

提交级覆盖的三条反向对照，全部实测变红：
忽略豁免行 / 把只「提到」`No-ADR` 的提交当成豁免 / 把 base 分支自己的提交算进范围。

自指那一半的证据是 1.7.12 那笔提交：新门禁判它 rc=1，同一范围内的合规提交 rc=0。
